# RailFlow — Manual QA Plan

| | |
| :--- | :--- |
| Project | RailFlow — rail route planner and booking (final project, Introduction to Functional Programming) |
| Application | .NET 10 Blazor Interactive Server app (`src/RailFlow.Web`) |
| Document owner | RailFlow team |
| Related | `README.md` (features, automated tests), `docs/DEPLOYMENT.md` (how to run the build under test) |

The automated suite (`dotnet test`) covers the functional core, storage and the API. This plan covers what only a person in a browser can check: the UI flows, roles, real-time updates, accessibility, layout and browser compatibility.

---

## 1. Scope

**In scope**

- The tabs, which depend on who is signed in and on the **Course notes** switch in the header:
  - everyone: **Plan a trip**, **Bookings**, **Timetable**;
  - dispatchers also get the group **Operations** with **Network** and **Dispatcher** (guests and passengers do not have these tabs at all);
  - with **Course notes** switched on, everyone also gets the group **Course** with the **Lab** tab (deep recursion, route cache, station data check, loop benchmark), plus the "How it works" notes, the "How the search ran" trace and the edge-case links on **Plan a trip**.
- The open tab is part of the address (`?tab=bookings`, `?tab=timetable`, `?tab=network`, `?tab=dispatcher`, `?tab=lab`; **Plan a trip** has no `tab` part): links, reload, Back / Forward, a tab the visitor may not open, and keyboard navigation between the tabs (arrow keys, Home, End).
- The travel date on **Plan a trip** (default, past date) and where it is shown: result, **Timetable**, **Bookings**, tickets.
- Sign in / sign out with the demo accounts, role-based visibility (guest, passenger, dispatcher), and the booking rules: a passenger sees the bookings of their own account (also after a reload or a new session), a guest sees only the bookings made in the current browser tab, a dispatcher sees all.
- Success and failure paths: unknown station (`Nothing`), simulated service failures (`Error`), trip and booking validation, promo codes, payment outage and card limit, and the same trip not being payable twice after a price update.
- Booking storage in JSON and text format (dispatchers), ticket preview and download in three formats, persistence across restarts.
- Network CSV import with rejected lines, the recursive timetable and journey progress, and the **Lab** experiments (200,000-section recursion, route cache, station data check, loop benchmark).
- Endpoints used from the browser: `/api/route-quote` (including its 400 answers), `/api/bookings` and `/api/bookings/{id}/ticket` (both dispatcher-only), `/healthz`, `POST /login` (rate limit), `POST /account/logout`, the "Page not found" page, SignalR `/hubs/traffic`.
- Keyboard-only use, dark mode, 375 px mobile width, reconnect dialog after a server restart.

**Out of scope**

- Load and performance testing beyond the loop benchmark in the **Lab** tab.
- Real payments (the payment gateway is simulated), real e-mail delivery.
- Multi-instance deployment (the app is single-instance by design, see `docs/DEPLOYMENT.md` section 8).
- Penetration testing; only the basic access-control and rate-limit checks listed below.

## 3. Preparation

1. Start the app with an **empty booking folder**, so earlier data does not affect the results:
   - `dotnet run`: `$env:Storage__BookingDirectory = "$env:TEMP\railflow-qa"; dotnet run --project src/RailFlow.Web` → `http://localhost:5163`
   - Docker: `docker run -d --name railflow -p 8080:8080 -v railflow-qa:/app/data railflow:latest` → `http://localhost:8080`
2. Demo accounts: passenger `passenger` / `passenger-demo` (shown as **Demo Passenger**), dispatcher `dispatcher` / `dispatcher-demo` (shown as **Demo Dispatcher**).
3. **Dispatcher settings are shared by all users and kept until restart.** At every start, engineering works are already switched on at **Frankfurt** and **Lyon**, so the default trip London → Zurich (via Paris and Lyon) shows an engineering works advisory and a surcharge. After every test that changes a switch on the **Dispatcher** tab, put it back (or restart the app) before the next test.
4. **Course notes** is off in every new browser session and after every page reload. Tests that need it say "Course notes on"; switch it on in the header first.
5. The trip form opens with London → Zurich, **Date** = tomorrow, departure 08:00, 2 passengers, package **Alpine package, 4 nights**, and already shows the result for it. Where a test needs known amounts, it uses package **Single ticket**: with the default dispatcher settings that trip is Rail fare €589.60 + Engineering works surcharge €38.72 = **€628.32** (the date does not change the price).
6. Dates on screen depend on the day of testing. The examples use `Sat 14 Nov` as "tomorrow"; check against the real tomorrow (the format is weekday, day, month, for example `Sat 14 Nov`, and with the year `Sat 14 Nov 2026` where noted).
7. For two-window tests use two different browsers, or one normal and one private window (the sign-in cookie is per browser profile).
8. The **Activity** list on the **Dispatcher** tab belongs to the open browser tab (it starts again after a reload), keeps the 15 newest entries, and shows UTC times.
9. Sign-in attempts are limited per client address (default 10 `POST /login` requests per minute). Run **TC-42** last, and wait one minute afterwards before signing in again. To make it quicker, start the app with `Security__LoginAttemptsPerMinute=3`. Testers behind the same address (office network) share one limit.

**Result values:** `Pass`, `Fail (D-nn)` with the defect ID from section 5, `Blocked`, `N/A`. Leave a cell empty until the test has been executed.
